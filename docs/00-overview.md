# 00. 개요 (Overview)

> 이 리팩토링이 **무엇을 위해, 무엇이 되면 성공인가**를 정의한다.  
> 나머지 모든 문서·ADR·코드는 여기서 정의한 목표·성공기준을 향한다.  
> 기준일: 2026-07-01. 성공 기준의 구체 수치는 `[조정 필요]`로 표시(사용자 확정 대상).

## 1. 프로젝트

- **FRANS** — 프랜차이즈 주문관리 ERP(본사 ↔ 가맹점). 원래 6인 팀 프로젝트.
- **스택**: Spring Boot 3.2.5 / Java 17 / MariaDB / Redis. CQRS(command=JPA, query=MyBatis).
- **규모**: Java 493 파일, 약 21.7k LOC, 도메인 22개.
- **이 작업**: 단독 리팩토링. 기간 약 2개월(2026-06 ~ 2026-08).

## 2. 왜 하는가 (목적)

**취업 포트폴리오.** 팀으로 만든 것을 단독으로 리팩토링하며 아래 4가지를 코드와 문서로 증명한다.

1. **도메인 설계** — Anemic → Rich Domain (결재 엔진).
2. **동시성** — 낙관적 락 / 분산 락으로 경합을 다룬다.
3. **회복탄력성** — 외부 의존(Redis 등) 장애에 견딘다.
4. **AI 활용** — 단순 API 호출이 아닌, 비용·신뢰성을 고려한 하이브리드 설계(이상 주문 감지).

> 특히 4번(AI)은 "남들과 다른 관점"을 어필하는 1순위 포인트다. 상세는 `05-ai-anomaly-detection.md`.

## 3. 범위 (Scope)

전체 22개 도메인을 다 건드리지 않는다. **깊게 파는 소수 + 얕게 손대는 것**을 구분한다.

- **집중(깊게)**: `approval`(결재 엔진) — 리팩토링의 중심.
- **관통(주제별)**: 동시성/회복탄력성/배치/AI가 필요한 지점(order 스케줄러, 통계, SSE 등).
- **손대지 않음**: 위와 무관한 도메인의 동작·구조.

근거: 프로젝트 전체를 얕게 훑는 것보다, 한 도메인을 깊게 재설계하는 편이 위 4가지를 더 강하게 증명한다.

## 4. 성공 기준 (측정 가능하게)

"리팩토링했다"가 아니라 **검증 가능한 결과**로 정의한다. 각 항목은 그 트랙 완료의 판정 기준이다.

| 영역 | 성공 기준 | 측정 방법 |  
|---|---|---|  
| 결재 도메인 | `ApprovalCommandServiceImpl` 867줄 → **[조정 필요: 예 200줄 이하]**, 상태전이 100% 애그리거트로 이동 | 라인 수, `setStatus` 외부 호출 0건 |  
| 안전망 | 결재 핵심 플로우(생성/승인/반려/재상신) 특성화 테스트 존재, 전체 빌드 그린 | CI 그린, 커버리지 **[조정 필요]** |  
| 외부 동작 보존 | 리팩토링 전후 API 응답·DB 상태 동일 | 특성화 테스트 통과(01 §5) |  
| 동시성 | 동시 승인 시 이중 완료 **0건** | 부하 테스트(동시 요청 N) |  
| 회복탄력성 | Redis 장애 주입 시 fallback 동작, 전체 실패로 번지지 않음 | 장애 주입 테스트, CircuitBreaker 상태 전이 확인 |  
| AI 이상탐지 | precision **[조정 필요]** 이상, LLM 호출은 1차 필터 통과분만 | 평가셋 precision, 호출 건수/비용 |  
| CI/CD | PR·develop push마다 자동 검증(그린) | GitHub Actions |  

> 수치는 초안이다. W0 마무리 전 네가 확정한다(포트폴리오에서 강조할 지표 위주로).

## 5. 비목표 (Non-Goals) — 명시적으로 안 하는 것

- 전체 도메인 리팩토링(범위 밖 도메인 구조 개선 금지 — CLAUDE.md §3).
- 신규 기능 추가(리팩토링이지 기능 개발이 아님).
- 프론트엔드/UI 작업.
- AWS 재배포(CD는 봉인, CI만 운영 — `project_cicd_setup` 방침).
- "편의를 위한" 스키마/동작 변경(허용 조건은 01 §5.2).
