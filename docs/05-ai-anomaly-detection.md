# 05. AI 이상 주문 감지 (차별화 핵심)

> "AI를 어떻게 활용했는가"를 증명하는 문서. 단순 API 호출이 아니라
> **비용·신뢰성을 설계한 하이브리드 파이프라인**으로 접근한다.
> 기준일: 2026-07-21. 그린필드(아직 코드 없음) — 이 문서가 구현의 설계 근거다.
> 모델·수치 관련 사실은 `claude-api` 스킬 기준으로 검증. 수치 목표는 `[조정 필요]`.

## 1. 문제 정의

프랜차이즈 본사 관점에서 **비정상 주문**(평소 패턴을 크게 벗어난 금액·수량·빈도)을 조기에 감지해 알린다.
예: 특정 가맹점의 월 주문금액이 자기 이력 대비 급증, 반품 비율 이상 등.

## 2. 관점 — 왜 "LLM에 다 맡기지" 않는가

이 프로젝트의 차별화는 **LLM을 외과적으로만 쓰는 것**이다.

- 이상치의 **1차 스크리닝은 통계로 충분하다** — 모든 주문을 LLM에 넣는 건 비용·지연·환경 낭비.
- LLM은 통계가 못 하는 **"왜 이 이상치가 실제로 의심스러운가"의 맥락 판단**에만 투입한다
  (예: 신규 오픈 가맹점의 급증은 정상, 폐점 직전 급증은 의심 — 통계 임계값만으론 구분 못 함).
- 즉 **통계 = 재현율(빠짐없이 거름), LLM = 정밀도(맥락으로 걸러냄)** 의 역할 분담.

> 면접 방어 라인: "AI 썼어요"가 아니라 "**비용을 제어하며 통계의 한계를 LLM으로 보완**했고,
> LLM이 죽어도 통계로 degrade되게 설계했다"가 핵심 서사.

## 3. 3단계 하이브리드 파이프라인

```
[주문/통계]
   │
   ▼ 1차) 통계 z-score 필터  ← LLM 호출 없음 (저비용, 전수)
   │      FranchiseOrderAmountStat 이력으로 baseline(μ, σ) 계산 → |z| ≥ 임계치만 통과
   ▼ 2차) LLM 맥락 판단      ← 1차 통과분만 (비용 제어의 핵심)
   │      structured JSON 출력(의심여부·사유·신뢰도), 프롬프트 캐싱
   ▼ 3차) SSE 실시간 알림     ← 05는 04-resilience/W5 SSE 확장 위에 얹힘
[담당자]
```

### 3.1 1차 — 통계 z-score 필터 (LLM 없음)

- 재료: `statistics` 도메인의 기존 통계 테이블 재활용.
  - `FranchiseOrderAmountStat`(가맹점별 **월** 주문금액) → 가맹점 이력으로 μ, σ 산출 → z-score.
  - 보조: `FranchiseProductOrderStat`(품목), `FranchiseReturnProductStat`(반품).
- 판정: `|z| ≥ threshold`(예 3.0 **[조정 필요]**)인 건만 2차로.
- 이점: 전수 검사이지만 비용 0(LLM 미호출), DB 통계만 사용.

> **정직한 한계(설계 고려)**: `FranchiseOrderAmountStat`은 **월 집계**다. 따라서 z-score의 자연스러운
> 단위는 "이번 달 총액이 이 가맹점 이력 대비 이상한가"이다. **개별 주문 실시간**을 보려면
> 별도 per-order baseline이 필요 — 초기엔 월 단위로 시작하고, 실시간 per-order는 후속 확장으로 분리한다.
> (이 granularity 트레이드오프 자체가 설계 논점이며 ADR로 남길 후보.)

### 3.2 2차 — LLM 맥락 판단 (의심건만)

- **입력**: 1차 통과 건 + 맥락(가맹점 오픈일·최근 추세·반품이력 등 구조화 데이터).
- **출력**: **structured outputs(JSON schema)** 로 `{ suspicious: bool, reason: string, confidence: number }`.
- **결정성 확보 방식(정정된 사실)**: 최신 Opus(`claude-opus-4-8`/`4-7`)는 `temperature` 파라미터가
  **제거**되어 `temperature: 0`을 보내면 400 에러다. 결정성/파싱 안정성은 **temperature가 아니라
  structured outputs(JSON schema, 스키마 강제)** 로 얻는다. (구형 모델에서만 temperature 사용 가능.)
- **모델 선택(결정 필요, ADR 후보)**: 비용 vs 정확도 트레이드오프.
  - `claude-haiku-4-5`($1/$5 per MTok) — 저비용, 2차 대량 스크리닝에 적합.
  - `claude-sonnet-4-6`($3/$15) — 균형.
  - `claude-opus-4-8`($5/$25) — 최고 정확도, 애매건 에스컬레이션용.
  - 후보 설계: **Haiku로 2차 대부분 처리 → 신뢰도 낮은 애매건만 Opus 에스컬레이션**(모델 티어링).
    최종 선택은 평가셋 precision을 보고 `[조정 필요]`.

### 3.3 3차 — SSE 실시간 알림

- 2차에서 `suspicious=true`로 판정된 건을 담당자에게 실시간 push.
- `04-resilience`/W5의 **SSE Redis Pub/Sub 다중 인스턴스 확장** 위에 얹는다(별도 구축 아님).

## 4. 설계 결정 & 방어 포인트 (각 항목 ADR 후보)

| # | 결정 | 근거 | 트레이드오프 |
|---|---|---|---|
| A1 | 통계 1차 → LLM 2차 하이브리드 | 전수 LLM은 비용·지연 과다 | 1차 임계값이 낮으면 2차 비용↑, 높으면 재현율↓ |
| A2 | LLM은 1차 통과분만 호출 | 비용 제어 핵심 | 1차가 놓친 이상은 LLM까지 못 감 |
| A3 | 프롬프트 캐싱 | 시스템 프롬프트·few-shot 고정부 재사용으로 비용↓ | 캐시 최소 프리픽스 충족 필요(모델별 2K~4K 토큰) |
| A4 | 결정성 = structured outputs(JSON schema) | 최신 모델은 temperature 미지원 | 스키마 제약(재귀·수치범위 등 일부 미지원) |
| A5 | LLM 실패 시 z-score로 degrade | 회복탄력성(외부 의존 장애) | degrade 시 정밀도 하락 수용 |
| A6 | 모델 티어링(Haiku→Opus 에스컬레이션) | 비용/정확도 균형 | 라우팅 복잡도 증가 |
| A7 | 평가셋 + 피드백 루프 | precision 측정·개선 | 라벨링 비용 |

> A5는 `04-resilience`(Resilience4j CircuitBreaker)와 직접 연결 — LLM 호출에 CB를 걸고,
> open 상태면 z-score 결과만으로 판정(fallback). A3는 `claude-api` 프롬프트 캐싱 규약을 따른다.

## 5. 트랜잭션·아키텍처 제약 (CLAUDE.md §5와 연결)

- **LLM 호출은 트랜잭션 안에서 하지 않는다.** 주문 저장 트랜잭션과 분리해
  도메인 이벤트 `AFTER_COMMIT`에서 파이프라인을 트리거한다(결재 D4와 동일 원칙).
- 구현: Spring Boot이므로 **anthropic-java SDK**(`com.anthropic`) 사용.
  2차는 structured outputs(POJO 스키마 자동 유도)로 타입 안전하게 파싱.
- 배치 백필: 과거 데이터 소급 분석은 실시간이 아니므로 **Message Batches** 고려(비용↓).

## 6. 평가 (성공 기준, 00 §4 연결)

- **평가셋 구축**: 과거 주문 중 이상/정상 라벨링(소규모라도) → precision/recall 측정.
- 목표: precision `[조정 필요]` 이상, LLM 호출은 1차 통과분만(호출 건수·비용 로깅).
- **피드백 루프**: 담당자가 알림을 "실제 이상/오탐"으로 표기 → 임계값·프롬프트 개선 신호로 사용.
- 초기엔 수치 목표보다 "**평가셋 구축 + precision 측정 파이프라인 존재**" 자체를 기준으로 둔다(정직).
