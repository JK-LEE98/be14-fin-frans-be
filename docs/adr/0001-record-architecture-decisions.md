# 0001. 아키텍처 결정을 ADR로 기록한다

- 상태(Status): 채택됨(Accepted)
- 날짜: 2026-07-01

## 맥락 (Context)

FRANS 리팩토링은 코드 구조를 크게 바꾼다(결재 엔진 재설계, 동시성, 회복탄력성, AI 활용).  
이런 결정들은 코드만 봐서는 **"왜 그렇게 했는가 · 어떤 대안을 버렸는가 · 무엇을 감수했는가"**가 남지 않는다.  
시간이 지나면 결정 이유를 잊고, 이미 내린 결정을 다시 뒤집는 낭비가 생긴다.

또한 이 프로젝트는 취업 포트폴리오다. "결정할 때 대안을 비교하고 트레이드오프를 기록한다"는  
사고 과정 자체가 어필 포인트이며, 그 근거가 리포지토리에 남아 있어야 한다.

## 결정 (Decision)

의미 있는 아키텍처/설계 결정을 **ADR(Architecture Decision Record)**로 기록한다.

- 위치: `docs/adr/`
- 파일명: `NNNN-kebab-case-title.md` (번호는 4자리, 증가만 함)
- 형식: 맥락 / 결정 / 대안 / 결과(트레이드오프) 중심 (Michael Nygard 스타일)
- 1 파일 = 1 결정
- 한 번 채택된 ADR은 수정하지 않는다. 결정이 바뀌면 **새 ADR을 쓰고 이전 것을 "대체됨(Superseded by NNNN)"**으로 표시한다(히스토리 보존).

## 대안 (Alternatives)

- **아무것도 안 남긴다(코드만)**: 가장 흔한 상태. "왜"가 사라져 결정 재litigation이 반복 → 기각.
- **위키/노션에만 정리**: 코드와 분리돼 동기화가 깨지기 쉽고, 리뷰어가 리포지토리에서 못 봄.  
  (옵시디언은 "포트폴리오 서사"용으로 별도 유지하되, 설계 결정의 ground truth는 리포지토리에 둔다.)
- **커밋 메시지에만 기록**: 결정 단위로 찾기 어렵고 대안/트레이드오프를 담기엔 좁음.

## 결과 (Consequences)

- 얻음: 결정의 근거가 코드 옆에 남아, 미래의 나·리뷰어·Claude Code가 맥락을 공유한다.
- 얻음: "식별 → 대안 비교 → 선택 → 트레이드오프"의 사고가 문서로 증명된다.
- 비용: 결정마다 짧은 문서를 쓰는 습관이 필요하다(대신 사소한 것까지 쓰지는 않는다).
